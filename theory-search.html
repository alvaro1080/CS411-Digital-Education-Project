FIRST, A TOOL FOR COMPARING ALGORITHMS

Time complexity and Big O notation

When we compare algorithms, we do not only ask whether they work. We also ask how much effort they need as the input becomes larger. This is the idea behind time complexity: it describes how the running time of an algorithm grows as the number of items increases. In our examples, n represents the number of elements in the list.

Some algorithms are fast even on very large inputs, while others become much slower as the data grows. Time complexity gives us a way to describe this growth in a simple and useful form. For a particular input size, the best-case running time is the least amount of work the algorithm needs across all possible inputs of that size; the worst-case running time is the greatest amount of work it may need. Comparing these cases helps us understand how the algorithm behaves on its easiest and most demanding inputs. Here, n is the number of elements in the array.

Big O notation is the standard language for that comparison. We write O(f(n)) to say that an algorithm's running time grows no faster than some function of n as the input becomes large. This gives us an upper bound on the growth rate. In practice, we ignore small constant factors and less important terms, because they do not change the main trend when the input is large. For example, an algorithm that takes 2n + 5 steps is still described as O(n), because the linear part dominates as n grows.

The purpose of Big O is not to give the exact number of operations in every situation. Instead, it gives a compact way to compare algorithm behavior. A list of all possible operations would be messy and hard to interpret. Big O lets us quickly see whether an algorithm scales well or whether it will become impractical as the input grows.

Common time complexity classes

O(1) Constant time: the number of operations stays bounded as the input grows, so the input size does not affect the amount of work.

O(log n) Logarithmic time: the number of operations increases slowly as the input grows; each operation reduces the remaining problem by a consistent proportion.

O(n) Linear time: the number of operations grows in proportion to the input size.

O(n log n) Linearithmic time: the number of operations grows in proportion to the input size multiplied by its logarithm, so it grows faster than linear time but slower than quadratic time.

O(n^2) Quadratic time: the number of operations grows in proportion to the square of the input size, making the work increase more rapidly as the input grows.

Working it out: linear search

Recall the first algorithm you saw (Linear Search). In the worst case, the target is last or is not in the list. A list of n items then needs at most n comparisons. The work grows in proportion to the list size, so the worst-case time complexity is O(n). If the first item is the target, it takes just one comparison: the best case is O(1), meaning constant work.

Example: with 10 items, linear search may need up to 10 comparisons; with 100 items, up to 100. The exact count can vary, but the growth pattern is linear.

Using Big O to compare our searches

Linear search has worst-case complexity O(n). Binary search has worst-case complexity O(log n), because each comparison lets it discard half of the remaining sorted list. For 16 items, that takes about 4 halving steps; for 1,024 items, about 10. So binary search usually needs fewer checks on a large list—but the list must already be sorted.

In the best case, both linear and binary search have complexity O(1): each finds the target on its first check. For linear search, this happens when the target is the first item in the list. For binary search, it happens when the target is exactly the middle item checked first. So although their worst cases differ greatly, both can be equally quick when the target is found immediately (assuming binary search's list is sorted).

L
ALGORITHM A

Linear Search

Linear search checks values one at a time from left to right. It is simple and flexible, but on a large list it may need to inspect many positions before it finds the target.

Best case O(1) Average case O(n) Worst case O(n)

Best case happens when the target is the first item checked. The algorithm works even when the list is unsorted.

B
ALGORITHM B

Binary Search

Binary search repeatedly splits a sorted list into halves and discards the half that cannot contain the target. This makes it much faster on large sorted inputs.

Best case O(1) Average case O(log n) Worst case O(log n)

Binary search depends on the list being sorted. If the data is not ordered, it can no longer safely ignore halves.

!
THE KEY IDEA

Same question, different strategy.

Linear search gives up little and works almost anywhere; binary search is much faster after sorting, because it throws away half the list each step.
